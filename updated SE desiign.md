## **Phase 2 — Database Management**

The database design is owned by the database/financial core phase and should retain the finalized Phase 2 design, with the following cross-phase corrections.

### **Database principles**

- SQLite as the single authoritative database.
    
- Direct SQL using parameterized queries.
    
- Transactions for atomic financial operations.
    
- Appropriate indexes and constraints.
    
- No ORM.
    

### **Financial integrity**

- Wallet balances must agree with ledger-derived balances.
    
- Financial operations must not partially commit.
    
- Ledger records must be immutable.
    
- Successful money movements must have balanced debit/credit entries.
    
- No successful transfer may create or destroy money.
    

### **Wallet lifecycle**

- User registration and wallet creation are one operation.
    
- Every newly created wallet begins with **zero balance**.
    
- Wallet is not independently created later through a separate API.
    
- Wallets cannot be deleted independently.
    

### **Failed transaction storage**

- Failed transfer attempts must be persisted.
    
- Failed attempts are not successful financial transactions.
    
- Failed attempts must not generate financial ledger entries.
    
- Failed attempts must not alter balances.
    

### **Idempotency**

Follow the finalized Phase 2 design:

- Idempotency is implemented for financial operations.
    
- Retries must not cause duplicate financial operations.
    
- A replay must follow the existing Phase 2/4 implementation behavior.
    
- Rejected requests follow the finalized Phase 2/4 key-consumption policy.
    

### **Admin funding**

- Funding is a separate operation from wallet creation.
    
- Admin funding is not tied to a user's registration.
    
- Remove the fixed ₹5 lakh allocation.
    
- Admin funding is a special financial operation with its own ledger representation.
    

### **Removed functionality**

- Wallet freeze fields and freeze-related state are removed.
    
- No freeze/unfreeze functionality.
    

## **Phase 3 — Security Management**

### **Authentication**

- User registration and login using email and password.
    
- Duplicate email registration is rejected.
    
- Passwords stored using bcrypt hashing.
    
- JWT authentication.
    
- JWT algorithm: HS256.
    
- Access token expiry: 1 hour.
    
- No refresh token.
    
- JWT secret stored in `.env`.
    

### **Roles**

Two roles:

- `user`
    
- `admin`
    

Admin is a specialized testing user with additional funding privileges.

### **User identity**

- Autogenerated unique User IDs, e.g., `USR-10001`.
    
- User ID is permanent.
    
- User ID is not used as a substitute for authentication.
    

### **User permissions**

Users can:

- View own profile.
    
- Edit permitted profile details.
    
- View own wallet and balance.
    
- Transfer money to other registered users.
    
- Search recipients by User ID/email.
    
- View their incoming and outgoing transaction history.
    
- Request account deletion.
    

Users cannot:

- Transfer from another user's wallet.
    
- Access other users' private financial history.
    
- Access admin functions.
    
- Create admin accounts.
    
- Modify financial ledger records.
    

### **Admin permissions**

Admin can:

- Search registered users by User ID or email.
    
- View basic user identification information (name + User ID).
    
- Fund a user's wallet.
    

Admin cannot:

- Perform ordinary user-to-user transfers through the admin funding operation.
    
- Access users' private transaction history.
    
- Access sensitive user profiles.
    
- Create other admins through the API.
    

### **Security practices**

- JWT verification.
    
- Role-based access control.
    
- Ownership checks.
    
- Input validation using Pydantic.
    
- Parameterized SQL.
    
- Secrets through environment variables.
    
- Generic client-facing error messages.
    
- No sensitive data, SQL, stack traces or secrets in logs.
    
- HTTPS outside trusted local development.
    
- CI secret scanning.
    

## **Phase 4 — Financial Transaction Management**

### **Ordinary transfers**

**Transfer rules**

- Sender initiates the transfer.
    
- Recipient does not need to be online.
    
- Only registered users can receive transfers.
    
- No self-transfers.
    
- Transfers are all-or-nothing.
    
- Transactions use ACID properties.
    
- Insufficient balance → reject.
    
- No automatic retry of insufficient balance.
    
- Idempotency prevents duplicate execution.
    
- Amounts stored in integer paise.
    

### **Transfer limits**

|Rule|Limit|
|---|---|
|Maximum per transfer|₹50,000|
|Maximum successful outgoing transfers per day|₹1,00,000|
|Failed transfer contribution to daily limit|₹0|

The daily limit applies to the sum of **successful outgoing transfers**.

### **Transfer processing**

For a successful transfer:

1. Validate the request.
    
2. Authenticate sender.
    
3. Verify sender ownership of source wallet.
    
4. Verify recipient exists.
    
5. Reject self-transfer.
    
6. Validate amount and limits.
    
7. Check sufficient balance.
    
8. Execute the debit and credit atomically.
    
9. Write corresponding ledger entries.
    
10. Store the successful transaction.
    
11. Commit.
    

If any financial step fails, the transfer must not partially execute.

### **Ledger**

Every successful transfer produces corresponding debit and credit entries.

- Debit sender.
    
- Credit recipient.
    
- Entries must balance.
    
- Ledger is immutable.
    
- No successful transfer can produce money creation/loss.
    

### **Failed transfers**

- Failed transfer attempts are persisted.
    
- They do not create ledger entries.
    
- They do not change wallet balances.
    
- They do not count towards the daily outgoing limit.
    
- The attempt is visible to both involved users in their transaction history.
    
- Users see amount and status, not the internal failure reason.
    
- Internal diagnostics may retain the failure reason securely.
    

### **Admin funding**

Admin funding is separate from user transfers.

- Admin searches by User ID.
    
- Admin selects the user to fund.
    
- Funding credits the user's wallet.
    
- Funding is atomic.
    
- Funding has its own transaction/ledger representation.
    
- Admin funding is independent of wallet creation.
    
- Admin funding is not constrained by admin's wallet balance.
    
- Admin funding does not count toward the user's outgoing transfer limit.
    

### **Idempotency**

- Financial requests are idempotent.
    
- A retry must not execute the same operation twice.
    
- Repeated requests return the result of the original operation according to Phase 2/4 behavior.
    
- Rejected requests follow the finalized Phase 2/4 policy for idempotency keys.
    

## **Phase 5 — API Management**

Phase 5 is the authoritative design for API behavior and access.

### **API conventions**

- REST API.
    
- Prefix: `/api/v1/`
    
- FastAPI Swagger documentation at `/docs`.
    
- Consistent JSON responses.
    
- Appropriate HTTP status codes.
    
- Authentication and authorization enforced.
    
- Input validation.
    
- Bounded pagination.
    
- Newest-first transaction history.
    
- Filtering where applicable.
    
- Rate limiting on sensitive operations.
    

### **Authentication endpoints**

|Method|Endpoint|Purpose|
|---|---|---|
|POST|`/api/v1/auth/register`|Register user and create wallet|
|POST|`/api/v1/auth/login`|Authenticate|
|GET|`/api/v1/auth/me`|Current authenticated user|

### **User profile**

|Method|Endpoint|Purpose|
|---|---|---|
|GET|`/api/v1/users/me/profile`|View own profile|
|PATCH|`/api/v1/users/me/profile/edit`|Edit allowed profile information|

Profile rules:

- Name can be changed once every 60 days.
    
- Cooldown starts after a successful name change.
    
- Email is not editable.
    
- User ID is not editable.
    
- Account ID, if present, is not editable.
    

### **Wallet**

|Method|Endpoint|Purpose|
|---|---|---|
|GET|`/api/v1/wallet`|View wallet and balance|

Wallet rules:

- Automatically created during registration.
    
- Initial balance ₹0.
    
- No separate wallet creation endpoint.
    
- No wallet deletion.
    
- No wallet freeze.
    
- Wallet view includes balance.
    

### **Transfers**

|Method|Endpoint|Purpose|
|---|---|---|
|POST|`/api/v1/transfers`|Initiate a transfer|
|GET|`/api/v1/transfers`|View own transaction history|
|GET|`/api/v1/transfers/{transaction_id}`|View a specific transaction, subject to access rules|

Transfer history includes:

- Incoming and outgoing transactions.
    
- Successful and failed attempts.
    
- Transaction ID.
    
- Sender and recipient.
    
- Amount.
    
- Timestamp.
    
- Status.
    
- Direction.
    

History supports:

- Newest-first ordering.
    
- Pagination.
    
- Date filtering.
    
- Status filtering.
    
- Direction filtering.
    

Users can only view transactions involving themselves.

### **Admin funding**

|Method|Endpoint|Purpose|
|---|---|---|
|GET|`/api/v1/admin/users/search`|Search users by User ID/email|
|POST|`/api/v1/admin/funding`|Fund a user's wallet|

Admin user search reveals only basic identification information:

- Name
    
- User ID
    

Admin funding is independent of wallet creation and admin balance.

### **Account deletion**

- User must settle their balance first.
    
- Account deletion/deactivation follows the agreed retention policy.
    
- 7-day waiting period after deactivation.
    
- Eligible personal data is deleted after the retention period, subject to legal retention.
    
- Ledger data is preserved.
    
- Deactivated users cannot log in or transfer.
    

### **API implementation details**

The detailed request/response contract—including exact JSON schemas, validation, error codes and HTTP statuses—will be derived during implementation by Claude from this design. It is not a separate manual design phase.

## **Phase 6 — Reconciliation & Audit**

### **Purpose**

Verify that wallet balances, transaction records and ledger entries remain financially consistent.

### **Reconciliation checks**

**1. Wallet balance check**

Compare stored wallet balance against the balance calculated from ledger entries.

\[ \text{Expected balance}=\text{Credits}-\text{Debits} \]

**2. Transfer integrity**

Verify that successful transfers have the appropriate debit and credit entries.

**3. Ledger balancing**

Verify that each financial operation's debit and credit entries balance.

**4. Transaction consistency**

Verify that transaction status agrees with its financial ledger records.

**5. Funding integrity**

Verify that successful admin funding has the appropriate funding debit and wallet credit records.

### **Reconciliation behavior**

- Reconciliation is read-only.
    
- It does not automatically repair financial discrepancies.
    
- Detected discrepancies are recorded.
    
- Each reconciliation run has its own ID.
    
- Previous reconciliation reports are preserved.
    
- Admin can trigger reconciliation manually.
    
- No scheduled reconciliation is required initially.
    

### **Reconciliation reports**

Each report records:

- Reconciliation ID.
    
- Start time.
    
- Completion time.
    
- Status.
    
- Number of wallets checked.
    
- Number of transactions checked.
    
- Number of discrepancies.
    
- Details of discrepancies.
    
- Internal failure details, if the reconciliation run itself fails.
    

### **Reconciliation APIs**

|Method|Endpoint|Purpose|
|---|---|---|
|POST|`/api/v1/admin/reconciliation/run`|Trigger a reconciliation|
|GET|`/api/v1/admin/reconciliation/{reconciliation_id}`|View one report|
|GET|`/api/v1/admin/reconciliation`|List previous runs|

Only admin can access these operations.

### **Audit**

- Audit records are append-only.
    
- Reconciliation runs are retained.
    
- Financial ledger records are immutable.
    
- No automatic financial correction is performed by reconciliation.

### **Idempotency testing — aligned with Phase 2/4**

- Same idempotency key retry must not execute the financial operation twice.
    
- Repeated request follows the original Phase 2/4 behavior.
    
- Rejected requests follow Phase 2/4's key-consumption behavior.
    
- Phase 7 will **not introduce new idempotency rules** inconsistent with Phase 2/4.
    

### **Failed transfer testing**

- Failed attempts persist.
    
- Failed attempts do not create ledger entries.
    
- Wallet balances remain unchanged.
    
- Failed attempts don't consume daily successful transfer limit.
    
- Both involved users can see the attempt.
    
- Failure reasons aren't exposed to users.
    

### **Reconciliation testing**

- Correct wallet/ledger state → no discrepancy.
    
- Deliberately corrupted wallet balance → detected.
    
- Missing ledger entry → detected.
    
- Unbalanced ledger → detected.
    
- Incorrect transaction status vs ledger → detected.
    
- Reconciliation does not automatically repair the database.
    
- Failed reconciliation run is correctly recorded.

# **Final design changes from the previous version**

## **Decisions that supersede the old design**

- Wallet is created **automatically during registration**.
    
- Wallet starts with **₹0**.
    
- Wallet creation and admin funding are **independent**.
    
- No separate wallet creation endpoint.
    
- Admin can fund by searching User ID.
    
- Admin funding does not depend on admin wallet balance.
    
- Removed fixed ₹5 lakh funding allocation.
    
- Failed transfers are persisted.
    
- Failed transfers are not ledger movements.
    
- Transfer limits are ₹50,000 per transaction and ₹1 lakh daily successful outgoing.
    
- Removed wallet freeze completely.
    
- Removed notification implementation for now.
    
- Phase 5 is the authoritative API behavior.
    
- Phase 2/4 transaction implementation is retained; Phase 7 is aligned with it.
    
- Reconciliation is manual, read-only, discrepancy-reporting and admin-only.
    
- No automatic reconciliation repair.
    
- No reversal feature.
